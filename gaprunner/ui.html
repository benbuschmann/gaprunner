How GapRunner works

Prod comes first. Prod is the always-on model GapRunner protects. When prod has been quiet for a while and a job can use the time, GapRunner puts prod to sleep (its weights move to CPU memory). The next request waits at the door while jobs step aside and prod wakes (typically a second or two), then it's answered as usual. Normally, only jobs that can step aside within a few seconds (the "most a request may wait" setting) run while prod sleeps; a job that gets stuck stepping aside is stopped hard after a short deadline, so prod can wake. During slow-wake prod a request may wait as long as a slow job takes to step aside.

Jobs use what prod isn't using. A job that fits beside prod runs alongside it; one that gives way pauses for a moment whenever prod is answering. A job that needs prod's memory runs only while prod sleeps, and only when the quiet is likely to last long enough to be worth it, learned from prod's own history.

Slow-wake prod is a period you open (1, 3 or 8 hours) when jobs that are slow to step aside may run while prod sleeps. Prod still answers, but a request may wait as long as such a job takes to step aside. No prod stops prod for the period so jobs get the whole GPU, and starts it again when the period ends. Jobs set to "only during slow-wake prod" run in either.

Buttons on a job

Start lets it run as soon as there's room. Queue lines it up behind another job: it starts by itself once that job finishes with no errors (a job's Details can change or clear what it waits for). Wind down stops it at its next saved point when its recipe can say when its work is saved (saved_cmd); otherwise it finishes its current run, which for long training can take days. Either way it won't start again until Start or Queue. Stop ends it now; a resumable job continues from its last checkpoint when you Start it again. Pause stops it exactly where it is, keeping its memory, and Resume continues from the same instant: nothing is lost, but its GPU memory stays in use. Measure runs it briefly to fill in its memory and its step-aside and come-back times.

Many jobs at once: tick jobs in the queue (shift-click for a range, or Select all) and act on all of them. Queue in order makes each start when the one before it finishes, in the order shown. Drag ⠿ to reorder. Clear hides finished jobs under Cleared; Start brings one back. The chips above the queue filter it; Active hides done and cleared jobs.

Runs: alongside prod, alongside prod giving way, only while prod sleeps, or only during slow-wake prod (or no prod).

What a job is doing

Running, giving way (paused for a moment while prod answers), paused (by you), starting, queued (waits for another job to finish), waiting (with the reason), winding down, wound down, waits for slow-wake prod, idea (not set up to run yet), done, failed (not retried), stuck (running but not progressing).

Prod

Answering, awake, asleep (wakes on the next request, typically in a second or two), off, starting, switching. A service can have several models; Switch stops the current one, freeing its GPU and CPU memory, and starts the other. Jobs can require a model and step aside when it stops serving.

Whole system

Prod only is the emergency brake: prod stays awake, every running job steps aside, nothing starts until you end it. Wind down all does Wind down on every running job and starts nothing new. Unknown GPU use is memory held by processes that aren't prod or a job. A claim in the config tells GapRunner about work started by hand, so it counts that memory (shown as "claim") or starts nothing while it runs. Every job has its own link: #jobs/<job name> opens its details, /log after it opens the log.

Memory

The shelf at the top is the GPU drawn to scale; striped blocks are paused or unknown. Every job says what it expects to use in GPU memory, CPU memory and disk, and its details show what it actually uses next to that. GPU memory comes from the driver, never from a job's own report.
